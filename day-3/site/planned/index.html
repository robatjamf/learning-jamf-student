DAY 1

Jamf 101

What it is, how it fits, why it matters. Click to expand.

What is Jamf? ▶
Jamf is an MDM (Mobile Device Management) platform built specifically for Apple devices — Macs, iPhones, iPads, and Apple TVs.

Think of it like a remote control for every Apple device in an organization. IT admins can enroll devices, push software, enforce settings, and wipe devices — all without touching them physically.

Key point: Jamf doesn't work on Windows or Android. It's Apple-first, which is why it's used heavily in schools, hospitals, creative agencies, and enterprises that have gone all-in on Apple.
What can Jamf actually do? ▶
Enroll
Automatically enroll new devices with zero-touch. Device comes out of the box, turns on, and configures itself.
Deploy
Push apps, profiles, and settings to any device or group of devices instantly — no user interaction required.
Secure
Enforce password policies, encrypt drives, remotely lock or wipe a lost/stolen device.
Report
See every device's status, software inventory, and compliance state in one dashboard.
Smart Groups — the secret weapon ▶
Smart Groups are dynamic device lists that update automatically based on rules you set.

Real life example: You create a rule — "any Mac running macOS older than 15.0". Every device that matches automatically joins the group. When a device updates, it drops out of the group. No manual list-keeping.

In the workshop, you updated an Extension Attribute via the API → the device matched the "Workshop Participants" Smart Group rule → it was automatically added to the group → this triggered a webhook. That's the power of Smart Groups driving automation.

DAY 2

API Bootcamp

Understand the concept with a real analogy. Then see the actual commands. Then get tested.

THE RESTAURANT ANALOGY
You
the client / app
→ order →
Waiter
the API
→ request →
Kitchen
the server / Jamf
→ food →
Your plate
the data / JSON

You don't walk into the kitchen yourself. The waiter (API) takes your order, talks to the kitchen (server), and brings back exactly what you asked for. APIs are the agreed-upon language between apps.

GET Read / Fetch

Like checking your Instagram feed — your phone asks the server "give me the latest posts" and gets data back. Nothing changes.

Jamf: GET /api/v1/computers-inventory

POST Create / Send

Like posting a tweet — you're sending new data to the server to create something new. Something that didn't exist before now exists.

Jamf: POST /api/v1/auth/token

PUT Update / Replace

Like updating your Spotify profile picture — you're replacing something that already exists with new data.

Jamf: PUT extension attribute value

DELETE Remove

Like removing a LinkedIn connection — you're telling the server to delete a relationship. Gone permanently.

Jamf: token invalidation

BEARER TOKEN — WHAT IS IT?

Think of a wristband at a music festival. You prove your identity at the gate (username + password → POST /auth/token). They give you a wristband (the token). For the rest of the day, you just flash the wristband — no need to prove who you are again at every drink stand. The wristband expires when the festival ends. The token works the same way.

// show real commands from the workshop ▶
Step 1 — Get a token
curl -s -u "jamfpro_api:eap.zog.neek26" \ -H "Content-Type: application/json" \ -X POST \ "https://projsadp.jamfcloud.com/api/v1/auth/token"
Step 2 — Save token to a variable
TOKEN=$(curl -s -u "jamfpro_api:eap.zog.neek26" \ -H "Content-Type: application/json" \ -X POST \ "https://projsadp.jamfcloud.com/api/v1/auth/token" \ | jq -r '.token')
Step 3 — List all computers (GET)
curl -s \ -H "Authorization: Bearer $TOKEN" \ "https://projsadp.jamfcloud.com/api/v1/computers-inventory" \ | jq .
Step 4 — Update Extension Attribute (PUT via Classic API)
curl -X PUT \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/xml" \ "https://projsadp.jamfcloud.com/JSSResource/computers/id/YOUR_ID" \ -d '<computer> <extension_attributes> <extension_attribute> <id>1</id> <value>Butjilo</value> </extension_attribute> </extension_attributes> </computer>'
Step 5 — Invalidate token (security best practice)
curl -X POST \ -H "Authorization: Bearer $TOKEN" \ "https://projsadp.jamfcloud.com/api/v1/auth/invalidate-token"

DAY 2 — FOCUS AREA

Webhooks

This was the fuzziest topic. Let's fix that. Start with the real-world analogy, then trace the full Jamf flow.

THE VENMO ANALOGY — PUSH vs PULL
Polling (old way — PULL)

Imagine checking your Venmo app every 5 seconds asking "did anyone send me money yet?" That's polling — constant checking, most of it wasted.

Webhooks (smart way — PUSH)

Instead, you tell Venmo: "when someone sends me money, buzz my phone." Venmo fires a notification the instant it happens. You don't ask — it tells you. That's a webhook.

The doorbell version: Your front door doesn't call you every 30 seconds to ask "is anyone there?" You install a doorbell — it rings exactly when someone arrives. The doorbell URL is your webhook endpoint.

The exact flow from the workshop:
1
You ran a PUT curl command to update the Extension Attribute on your device to your name ("Butjilo").
2
Jamf Pro evaluated its Smart Group rules automatically. "Workshop Participants" rule matched your device.
3
Your device was added to the group. Jamf fired the SmartGroupComputerMembershipChange event.
4
Jamf sent a POST request to your webhook.site URL — the JSON payload arrived in real-time.
✓
You watched it appear live on webhook.site — no refresh needed. Event-driven in action.
The actual webhook JSON payload:
// This is what appeared in webhook.site when your device joined the Smart Group { "webhook": { "id": 1, "name": "Workshop Participants Webhook", "webhookEvent": "SmartGroupComputerMembershipChange" // ↑ This is the event type that fired — membership changed }, "event": { "groupAddedDevicesIds": [42], // ↑ Your device ID — added to the group "groupRemovedDevicesIds": [], // ↑ Empty — no devices were removed this time "jssid": 1, "jssurl": "https://projsadp.jamfcloud.com", // ↑ Which Jamf Pro server fired this "name": "Workshop Participants", // ↑ The Smart Group that changed "smartGroup": true } }

DAY 2

Virtual Machines

Quick reference — the key concepts and config specs.

What is a VM? ▶
A VM is "a computer inside a computer."

Real life analogy: Like running a game emulator — your PlayStation emulator doesn't need a real PlayStation. It simulates the hardware in software. A VM does the same thing for an entire computer: it simulates CPU, RAM, disk, and network in software so you can run a completely separate operating system inside your existing one.

In the workshop you ran a full macOS VM inside your M-series Mac to test Jamf enrollment without touching your real machine.
VM Config Specs ▶
CPU4 cores
RAM8 GB
Disk50 GB
SourceIPSW file

Tool used: Virtual Buddy (lighter, ~50MB vs VMware's 500MB). macOS 15 and macOS 26 IPSW files from USB stick.

Snapshot = Save point ▶
Taking a snapshot is like creating a restore point in a video game before a difficult boss fight. If you enroll the VM in Jamf and something goes wrong, you can revert to "Clean install" — no reinstall needed.

Always name your first snapshot Clean install before doing anything. That's your safety net.

Compound Engineering Loop

The 4-step framework for working with AI. Not just for this workshop — for everything you build.

01 Plan

Define exactly what you're building before you start. Answer: "Do I have enough context to build this?" 80% of the work happens here.

→ What are we building? What context exists? What decisions need a human?

02 Work

Execute with AI assistance while staying within the plan. The remaining 20%. Ask: "Am I drifting from what I planned?"

→ Build. Reference the plan. Don't let AI improvise beyond scope.

03 Review

Check the output against your plan. Your eyes and judgment are the primary review tool — not the AI's. Ask: "Does this match what I intended?"

→ Read every line. Ask the agent: "what did you miss or change?"

04 Compound

Type /compound at the end of each session. Distill what you learned into COMPOUND.md so the next session inherits all your decisions.

→ What decisions did I make? What dead ends did I hit? What should next session know?
