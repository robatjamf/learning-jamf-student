Day 2 — APIs

Here is how computers talk to each other.

You are sitting at a restaurant. You do not walk into the kitchen and make your own food. You tell the waiter what you want, the waiter takes it to the kitchen, and the kitchen sends the food back through the waiter.

An API is the waiter. Your app is you. The server is the kitchen. The API carries the request in, and carries the data back. It is a two-way connection.

👤 You (Client) Postman / app
GET / POST →
🍳 API (Waiter) Jamf API
request →
🏠 Server (Kitchen) Jamf Pro
data back ←
🍽 Response JSON data
The two most important request types

GET — ask for something. "Show me the list of users."

POST — send something new. "Create this new user."

In Postman, I made a real API call that changed a Jamf Pro user's name — and watched it update live on the dashboard. That was the moment it stopped being theory.

Day 2 — The Hard Part

This one took me a while — Webhooks.

I am going to be honest: this was the topic that felt the fuzziest. So I am going to slow down here.

Imagine you ordered pizza. You could call the restaurant every five minutes asking "is it ready yet?" — that is exhausting for everyone. Or, you give them your phone number and they text you when it leaves. That text is a webhook.

The difference from an API call: you do not ask. The server tells you when something happens.

Pull (API Polling)

Your app asks: "Did anything change?"
Server: "No."
Your app asks again... and again...
Server: "Still no."
Wastes resources. Slow to react.

Push (Webhook)

You give the server a URL once.
Something happens in Jamf Pro.
Server instantly sends data to your URL.
Your app handles it in real time.
Efficient. Instant. The modern way.

What does the payload actually look like?

When the webhook fires, Jamf sends a JSON object to your URL. Here is a real example, with each part labelled:

Webhook Payload (JSON)
{
  "webhookEvent": "DeviceEnrolled"   ← what happened
  "timestamp":    "2026-03-06T09:14:22Z" ← when it happened
  "event": {
    "deviceName":   "Crown's MacBook Pro" ← the device
    "serialNumber": "C02XG2JHJGH7"       ← unique ID
    "udid":         "A1B2C3D4-..."         ← Apple device ID
    "username":     "crown"               ← who owns it
    "enrolled":     true                  ← boolean flag
  }
}

End-to-end: how it actually works

1

You register a URL in Jamf Pro

This is your "webhook endpoint" — the address Jamf will send data to when something happens.

2

An event fires in Jamf Pro

A device enrolls, a policy runs, a user changes. Jamf detects it.

3

Jamf sends a POST request to your URL

The payload (like the JSON above) arrives at your endpoint automatically.

4

Your app reads the payload and acts

Log it, send a Slack message, trigger another automation — whatever you built.

5

You respond with 200 OK

Your app tells Jamf "received" — otherwise Jamf will retry the delivery.

Day 3 — AI-Native Dev

Working with AI is not magic. It is a loop.

Going into Day 3, I wanted to understand AI — not just use it. The thing I did not expect: the output is only as good as the plan you give it.

We used a loop called the Compound Engineering loop: Plan → Work → Review → Compound. Two files anchor every session — CLAUDE.md for project context, COMPOUND.md for decisions and history that carry forward into the next session.

The lesson

AI does not replace thinking. It amplifies it. If you plan well, AI builds well. If you do not plan, you get something random — fast.
