Key Concepts — Step by Step
1
What is MDM?
MDM (Mobile Device Management) lets IT teams manage many Apple devices from one place — pushing settings, installing apps, and enforcing security rules without touching each device. Jamf Pro is Apple's premier MDM platform, designed specifically for Apple hardware and built around Apple's own best practices.
terminal 
Without MDM: IT visits each Mac manually to install software, set configs, enforce passwords
With MDM:   IT sends one policy from Jamf Pro → it applies to 1,000 Macs automatically

Jamf Pro manages:
  - macOS Macs (including Apple Silicon M-series)
  - iPhones and iPads
  - Apple TVs
Why it matters
Every API call, webhook, and automation you built in Days 2–3 exists to make MDM tasks faster and less manual.
2
Zero Touch Deployment
A device can be fully configured the moment a user turns it on — without IT ever touching it. The Mac enrolls in Jamf Pro automatically on first boot, downloads policies, installs apps, and sets security configs. The user just logs in and starts working.
terminal 
Flow:
  New Mac shipped to user
       ↓
  User powers it on → macOS Setup Assistant runs
       ↓
  Device detects DEP (Device Enrollment Program) profile
       ↓
  Auto-enrolls in Jamf Pro
       ↓
  Jamf pushes policies: apps, settings, restrictions
       ↓
  User logs in → fully configured Mac, no IT involvement
Why it matters
This is one of Jamf's biggest selling points — IT can scale to thousands of devices without a dedicated setup team.
3
Webhooks — Push vs Pull
Instead of constantly asking "did anything change?" (polling), webhooks let Jamf Pro notify an external system the moment something happens (pushing). You set up a webhook URL, and Jamf sends a JSON payload to it automatically when a trigger fires.
terminal 
Polling (bad):  Your script → "Any changes?" → Jamf → "No"
                Your script → "Any changes?" → Jamf → "No"
                Your script → "Any changes?" → Jamf → "Yes" ← wasted 100 requests

Pushing (good): Jamf → event fires → sends JSON to your webhook URL instantly

Workshop example:
  Trigger: Computer Added to Smart Group
  Webhook fires → sends JSON payload to webhook.site
  You see the device data appear in real time
Why it matters
Webhooks let you build real integrations — Slack alerts, ticketing systems, auto-remediation scripts — that react instantly without constant polling.
4
Extension Attributes
Custom data fields you add to computer records in Jamf Pro. You used one in the workshop (Workshop Status) to tag each computer with a participant's name, which then appeared in the Jamf dashboard and triggered a Smart Group.
xml 
# What you did in Day 2:
# Updated Extension Attribute ID 1 (Workshop Status) via API
# with your name → triggered Smart Group → fired webhook

curl -X PUT \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/xml" \
  "https://projsadp.jamfcloud.com/JSSResource/computers/id/YOUR_DEVICE_ID" \
  -d '<computer>
  <extension_attributes>
    <extension_attribute>
      <id>1</id>
      <value>Pride</value>
    </extension_attribute>
  </extension_attributes>
</computer>'
Expect
HTTP 201 — computer record updated. Your name now shows under "Workshop Status" in the Jamf Pro dashboard. If a Smart Group watches this attribute, the webhook fires.

Step-by-Step Walkthrough
1
Create your branch
Branches let you work in isolation without affecting anyone else on main. In the workshop, every student got their own branch — named students/<name> — so everyone could work at the same time without conflicts.
bash 
git checkout -b students/pride
Expect
Switched to a new branch 'students/pride'
2
Create your file
In the workshop, every student created a .txt file in the Students/ folder with their name and favorite animal. This was the actual change that got submitted as a PR to main. It proves the workflow — any change (code, config, docs) follows the same process.
bash 
echo "Name: Pride\nFavorite animal: ..." > Students/pride.txt

# Or open VS Code and create it manually:
code Students/pride.txt
Expect
No output — file now exists at Students/pride.txt. Confirm with: ls Students/
3
Stage the file
Staging is a checkpoint — you choose exactly what goes into the commit. You can have 10 changed files but only stage 2. Think of it as selecting which changes to seal in an envelope before sending.
bash 
git add Students/pride.txt

# Stage everything changed at once (use carefully):
# git add .

# Check what's staged:
git status
Expect
Changes to be committed: new file: Students/pride.txt
4
Commit
A commit is a permanent snapshot saved to your branch's history. The message should describe what changed and why — not just "update file". Anyone reading the git log should understand the change from the message alone.
bash 
git commit -m "add pride student file"

# See your commits:
git log --oneline
Expect
[students/pride abc1234] add pride student file 1 file changed, 2 insertions(+)
5
Push to GitHub
Your commits exist only on your local machine until you push. Pushing uploads your branch to GitHub so others can see it and so you can open a PR. The first push requires -u origin <branch> to link the local and remote branches.
bash 
git push origin students/pride

# After the first push, future pushes on this branch are just:
# git push
Expect
Branch 'students/pride' set up to track remote branch 'students/pride' from 'origin'. To https://github.com/.../learning-jamf-student.git * [new branch] students/pride -> students/pride
6
Open a Pull Request
A PR is a request to merge your branch into main. It creates a discussion thread where changes can be reviewed before they're accepted. In the workshop, you opened PRs so the facilitator (and you) could see all student files collected in one place.
bash 
# In GitHub UI:
# 1. Go to the repo on github.com
# 2. Click "Compare & pull request" (banner appears after push)
# 3. Set: base: main   ←   compare: students/pride
# 4. Title: "Add pride student file"
# 5. Click "Create pull request"
Expect
PR is created, shows as "Open" with your changes. Reviewers can comment on specific lines. Once approved → ready to merge.
7
Merge
Merging brings your branch's changes into main permanently. After merge, the branch can be deleted (the commits stay in main's history). Everyone else on the team can now git pull to get your changes.
bash 
# In GitHub UI:
# Click "Merge pull request" → "Confirm merge"

# Locally, update your main branch:
git checkout main
git pull
Expect
Pull request successfully merged and closed. Students/pride.txt is now in main — visible to everyone who pulls the repo.

Step-by-Step Walkthrough
1
Know your credentials & endpoints
The Jamf Pro REST API uses username/password to get a bearer token, which you then use for all subsequent requests. These are the workshop-only credentials — in production you'd use a dedicated API account with least-privilege permissions.
bash 
Username:  jamfpro_api
Password:  eap.zog.neek26
Instance:  https://projsadp.jamfcloud.com
Swagger:   https://projsadp.jamfcloud.com/api/doc

# Two API styles:
# Modern (v1, JSON):   /api/v1/...          ← preferred
# Classic (XML):       /JSSResource/...     ← needed for Extension Attributes
Why two APIs?
Jamf is migrating from an older XML-based API to a modern JSON API. Both still work. The modern API is /api/v1. The Classic API (/JSSResource) is still needed for things like Extension Attributes that haven't been migrated yet.
2
Get a bearer token
POST your credentials to the auth endpoint. Jamf validates them and returns a JWT token. You save it as a shell variable — $TOKEN — and pass it in every subsequent request. Tokens expire, so always get a fresh one at the start of a script.
bash 
TOKEN=$(curl -s -u "jamfpro_api:eap.zog.neek26" \
  -H "Content-Type: application/json" \
  -X POST \
  "https://projsadp.jamfcloud.com/api/v1/auth/token" \
  | jq -r '.token')

# What's happening:
# curl -s          = silent (no progress bar)
# -u "user:pass"   = basic auth for the initial token request
# -X POST          = HTTP method
# jq -r '.token'   = parse JSON response, extract just the token string
Expect
No visible output — $TOKEN now holds a long JWT string. Verify with: echo $TOKEN
3
Verify the token is set
Never assume the token was captured correctly. An empty $TOKEN means every subsequent request will fail with 401. Check it before proceeding — this saves debugging time later.
bash 
echo $TOKEN

# If empty — common causes:
# - jq not installed: brew install jq
# - Wrong credentials
# - Network issue reaching projsadp.jamfcloud.com
Expect
eyJhbGciOiJSUzI1NiJ9.eyJhdXRoZW50aWNhdGVkLWFwcCI6IkdFTkVSSUMi... (very long string) If blank → token capture failed. Re-run Step 2 and check for errors.
4
List all computers
This is a GET request — you're reading data, not changing anything. The Authorization: Bearer $TOKEN header is how every authenticated request works after the initial token exchange. jq . formats the raw JSON so it's human-readable in Terminal.
bash 
curl -s \
  -H "Authorization: Bearer $TOKEN" \
  "https://projsadp.jamfcloud.com/api/v1/computers-inventory" \
  | jq .

# Extract just the total count:
curl -s \
  -H "Authorization: Bearer $TOKEN" \
  "https://projsadp.jamfcloud.com/api/v1/computers-inventory" \
  | jq '.totalCount'

# Extract just the IDs and names:
curl -s \
  -H "Authorization: Bearer $TOKEN" \
  "https://projsadp.jamfcloud.com/api/v1/computers-inventory" \
  | jq '.results[] | {id, name: .general.name}'
Expect
{ "totalCount": 12, "results": [ { "id": "1", "udid": "...", "general": { "name": "MacBook-Pro", "lastContactTime": "..." } }, ... ] }
5
Get a single device
Once you have a device ID from the list above, you can query just that one device. This is useful when you want to inspect a specific computer's details — software, hardware, group memberships — before making changes.
bash 
curl -s \
  -H "Authorization: Bearer $TOKEN" \
  "https://projsadp.jamfcloud.com/api/v1/computers-inventory/YOUR_DEVICE_ID" \
  | jq .

# Get just the computer name:
curl -s \
  -H "Authorization: Bearer $TOKEN" \
  "https://projsadp.jamfcloud.com/api/v1/computers-inventory/YOUR_DEVICE_ID" \
  | jq '.general.name'
Expect
{ "id": "5", "udid": "...", "general": { "name": "MacBook-Pro", "lastContactTime": "2025-03-06T..." }, "hardware": { ... }, ... }
6
Update the Extension Attribute (triggers webhook)
This was the key Day 2 exercise — writing data back to Jamf. You used the Classic API (XML) to update Extension Attribute ID 1 (Workshop Status) with your name. Jamf evaluated the Smart Group criteria, added the device, and fired the webhook to webhook.site.
xml 
curl -X PUT \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/xml" \
  "https://projsadp.jamfcloud.com/JSSResource/computers/id/YOUR_DEVICE_ID" \
  -d '<computer>
  <extension_attributes>
    <extension_attribute>
      <id>1</id>
      <value>Pride</value>
    </extension_attribute>
  </extension_attributes>
</computer>'

# Then go to webhook.site to watch the payload arrive in real time
Expect
HTTP 201 — no response body. Check the Jamf Pro UI: your name appears under Workshop Status. webhook.site shows a new POST with JSON payload containing device info and the event type.
7
Invalidate your token
Always kill the token when you're done. This is a POST to a specific endpoint that tells Jamf to blacklist this token immediately — even if it hasn't expired yet. Good security hygiene, especially important in shared environments like the workshop.
bash 
curl -s -X POST \
  -H "Authorization: Bearer $TOKEN" \
  "https://projsadp.jamfcloud.com/api/v1/auth/invalidate-token"

# Confirm it's dead:
echo $TOKEN  # still in memory, but Jamf rejects it now
Expect
HTTP 204 No Content — no body returned. Token is now invalid server-side. Any request using it will get 401 Unauthorized.
Method / CodeWhat it means
GETRead/retrieve data — safe, makes no changes. e.g., list computers, get device details
POSTCreate something or trigger an action. e.g., get a token, create a device record, fire an action
PUTUpdate/replace existing data — replaces the whole resource. e.g., update Extension Attribute
PATCHPartially update a resource — only sends the fields you're changing (vs PUT which replaces everything)
DELETERemove something permanently. e.g., delete a device record
200 OKRequest succeeded and response has data
201 CreatedSomething was created successfully (e.g., new record)
204 No ContentSucceeded, but nothing to return (normal for DELETE, invalidate-token)
400 Bad RequestYour request is malformed — check payload format, headers, or URL
401 UnauthorizedToken is missing, wrong, or expired — re-authenticate and get a new token
403 ForbiddenAuthenticated but you don't have permission for this action
404 Not FoundThe resource or endpoint doesn't exist — check your URL and device ID
500 Server ErrorSomething went wrong on Jamf's end — try again or check Jamf logs

One-Shot vs Planned — What's the Difference?
One-Shot Build
You give Claude one big prompt and let it run. Fast to start, but the output reflects only what was in that first message. If your mental model of the problem was incomplete or unclear, the output will be too — and fixing it costs more time than planning would have.
bash 
# One-shot approach:
"Build me a review page for a 3-day Jamf Pro workshop."

# Claude builds something. It might look fine. But:
# - Did it cover all three days equally?
# - Does it use the formats you learn best from?
# - Does it include the actual commands you need to remember?
# Probably not — because you didn't tell it any of that.
Result
Faster to start. Output is generic. Harder to fix without restarting. Good for throwaway experiments.
Step-by-Step Walkthrough — The Compound Loop
1
Plan — before you write a single line
Define your goal. Transfer your mental model to the agent — what you're building, who it's for, what constraints exist, and what "done" looks like. Ask the agent questions before it does anything. This is where 80% of the value comes from. The plan IS the work.
bash 
"Look at my project and tell me what you see."
"What are we trying to build — explain it back to me."
"What questions do you have before we start?"
"What could go wrong with this approach?"
"What decisions do I need to make before you write code?"

# This page was built with a plan. The plan asked:
# - How do you learn? (examples)
# - What topics? (all three equally)
# - What study tools? (walkthroughs + flow diagrams)
# - What navigation? (tabs per topic)
Expect
Agent describes the project back to you, surfaces unknowns, asks clarifying questions. You answer them. Now it has real context — not just a task.
2
Work — execute within the plan
Let the agent build. Stay engaged — you're collaborating, not delegating. If it drifts from the plan, redirect it. If it surprises you, ask why before continuing. You should always be able to explain what the agent is doing and why.
bash 
"Build the page we planned — start with the HTML structure."
"Stick to what we agreed — don't add features we didn't discuss."
"Explain what you're about to do before you do it."

# Warning signs during Work phase:
# - Solution keeps growing unexpectedly
# - Agent says "Actually, let's try..." multiple times
# - You can't explain what it's building or why
Expect
Code, files, output generated. If something surprises you — pause and ask "Why did you do it this way?" before continuing.
3
Review — your eyes first, then ask
Open the output. Use it like a real person would — click things, read the content, scroll around. Your judgment comes first. Then ask the agent what it might have missed. This two-step review catches both visual and technical gaps.
bash 
# Step 1: Use it yourself
open day-3/site/planned/index.html

# Step 2: Compare to the plan
# - Does it have all 4 tabs? (Jamf Pro, Git, API, AI Dev)
# - Do flow diagrams show correctly?
# - Are full commands with expected output shown?
# - Is the quick reference expanded and useful?

# Step 3: Ask the agent
"Based on our plan, what did we miss?"
"Does this match what we agreed on?"
"What would a new user find confusing about this?"
Expect
You catch things the agent can't (how it feels to use it). Agent catches things you might miss (technical gaps vs the spec). Together = thorough review.
4
Compound — distill the session
Type /compound at the end of every session. Claude writes a summary of everything that happened — decisions made, dead ends hit, discoveries found. This gets stored in COMPOUND.md. The next session reads it and starts with full context instead of from zero.
bash 
/compound

# What gets saved to COMPOUND.md:
# - What we set out to build
# - Key decisions made (and why)
# - Dead ends encountered
# - Discoveries and things that worked
# - What the next session should know

# Two files — different purposes:
# CLAUDE.md     = lean project setup (agent reads this first every session)
# COMPOUND.md   = rich session history (context compounds over time)
Expect
COMPOUND.md updated. Next session opens Claude Code → reads CLAUDE.md + COMPOUND.md → starts with full context. No re-explaining needed.
PrincipleWhat it means in practice
Context is everythingOutput quality = context quality. Agent only knows what you tell it. Share your mental model, project history, constraints, and definition of "done".
Planning > building80% planning, 20% building. The plan IS the work. Execution is just confirmation. If you're watching code generate most of the time, you skipped the important part.
Share your mental modelThe agent doesn't have your picture of the problem. Transfer it: "Here's how I'm thinking about this..." / "The most important thing is..." / "The pattern we use is..."
Know when to quitSunk cost is a trap. Starting fresh with better context is faster than pushing through a bad path. Signs: solution keeps growing, agent keeps changing direction, you're confused.
It's a conversationCollaboration, not delegation. Back-and-forth: you share context → agent explores → agent proposes → you refine. Treat it like pairing with a smart colleague who needs your context.
Review against the planYour eyes and judgment are the primary review tool. Open output and use it like a real user. Then ask: "Based on our plan, what did we miss?"
Compound your sessionsDistill every session with /compound. COMPOUND.md = rich session history. CLAUDE.md = lean project setup. Next session inherits everything instead of starting from zero.
The paradigm shift from Day 3: Before AI tools — planning was easy, coding was hard. Now — planning is hard, execution is trivial. The bottleneck moved. Your value as a developer is now in the quality of your thinking and context, not in your typing speed.

AgentAn AI assistant that can take actions on your behalf — read files, write code, run commands, search the web
ContextEverything the agent knows about what you're trying to do — your project, history, constraints, goal
Context windowThe maximum amount of text an agent can "see" at once — like short-term memory. When it fills up, early parts are forgotten.
TokenSmall chunk of text (~1 word) the agent reads/writes. Context windows are measured in tokens (e.g., 200k tokens ≈ 150k words)
PromptWhat you type to the agent — your instruction, question, or context. Quality of prompt = quality of output.
HallucinationWhen the agent says something that sounds confident but is wrong or made up. Always verify factual claims.
Plan modeClaude Code feature: agent shows you exactly what it plans to do before doing it. You approve or reject.
Mental modelYour internal picture of the problem — what you understand about it. Transferring this to the agent is the key skill.
One-shot promptingGiving the agent a single big prompt with no back-and-forth planning. Fast but context-thin.
IterationGoing back and forth with the agent — refine, review, adjust, refine again. Better output than one-shot.
CLAUDE.mdProject setup file the agent reads first every session — keeps it lean: environment, commands, structure
COMPOUND.mdSession history file built by /compound — gets richer over time, gives next session full context
CompoundingEach session builds on the last. Context accumulates instead of resetting. Like compound interest — slow at first, then very powerful.
Warning signs — when to quit and start fresh:
Overcomplicated: solution keeps growing — more files, more steps, harder to follow
Context full: conversation is long, agent repeats itself or forgets earlier details
Direction changing: "Actually, let's try..." with no confident answer
You're confused: you can't explain what the agent is doing or why
Gut check: something feels off, even if you can't articulate it

Starting fresh with better context is always faster than pushing through a bad path.
