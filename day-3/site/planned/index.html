Day 2

VMs, APIs,
and webhooks.

Hands-on with real infrastructure. Enrolled a virtual Mac, made API calls, and watched events fire in real time.

💻

Virtual Machines

Used Tart to create a macOS VM, downloaded a configuration profile, and enrolled it in Jamf Pro.

“Your computer is a big house. A VM is one of the rooms inside — its own little house with its own rules.”

🔌

APIs

Made a POST request in Postman to create a new category in Jamf Pro.

First attempt: 401 Unauthorized — no bearer token. Fixed it, got the token, request succeeded.

APIs are like a restaurant waiter — they carry your request to the kitchen and bring the data back.

🔔

Webhooks

Watched a webhook fire automatically when a Smart Group membership changed.

The payload contained device data that looks opaque from the outside — unless you know the device IDs.

A webhook is a doorbell — you don’t check the door every 5 minutes; it rings when someone arrives.

“It finally made sense how virtual machines work, and I got to create my own, which I really enjoyed.”

What clicked on Day 2

What did I do with my Tart VM?
I downloaded a configuration profile on my VM and managed to enroll it in my Jamf Pro instance.
What API calls did I make in Postman?
I made a POST to create a new category and at first I received a 401 because I didn’t have a token — which means I wasn’t authorised. Once I got the token it worked and I successfully created a category for computers in Jamf Pro.
What I learnt about webhooks
Webhooks are a way to send feedback when an event has occurred. They are automatic and do not really require human input as much. The payload looked like a bunch of information — hard to read unless you know the device IDs.
What is still fuzzy?
The difference between webhooks and APIs. Theoretically I know the difference — webhooks are automatic, APIs need human interaction. But when doing it practically, I could not tell the difference between the API call and the webhook in the moment.

Still fuzzy? Let’s fix that.

API vs Webhook.

The theory is clear. Here’s a side-by-side to make the practical difference stick.

API

You ask. It answers.

Who starts it?
You do — your code sends a request
When?
Whenever you choose to call it
Analogy
Calling a restaurant to order food
Example you did
POST to create a Jamf category via curl
Webhook

It tells you. You listen.

Who starts it?
The server — when an event happens
When?
Automatically, the moment something changes
Analogy
A push notification landing on your phone
Example you saw
Jamf fired a payload when device joined Smart Group
💡

The practical tell: If you wrote curl or clicked “Send” in Postman, that was an API call. If you just watched something appear on webhook.site without doing anything, that was a webhook firing.

Reference

Commands you ran.

The actual curl commands from Day 2. Click to copy any of them.

1. Get a bearer token
curl -s -u "jamfpro_api:eap.zog.neek26" \ -H "Content-Type: application/json" \ -X POST \ "https://projsadp.jamfcloud.com/api/v1/auth/token"
2. Save the token to a variable
TOKEN=$(curl -s -u "jamfpro_api:eap.zog.neek26" \ -H "Content-Type: application/json" \ -X POST \ "https://projsadp.jamfcloud.com/api/v1/auth/token" \ | jq -r '.token')
3. List all computers
curl -s \ -H "Authorization: Bearer $TOKEN" \ "https://projsadp.jamfcloud.com/api/v1/computers-inventory" \ | jq .
4. Update an Extension Attribute (triggers the webhook!)
curl -X PUT \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/xml" \ "https://projsadp.jamfcloud.com/JSSResource/computers/id/YOUR_DEVICE_ID" \ -d '<computer> <extension_attributes> <extension_attribute> <id>1</id> <value>Amanda</value> </extension_attribute> </extension_attributes> </computer>'

Day 3

The Compound
Engineering loop.

A framework for working with AI that applies to any tool, now or in the future.

01 — Plan

Define before you build

Gather context, ask the agent questions, surface risks. The plan IS the work. Execution is confirmation.

02 — Work

Execute with AI

Build within the plan. Stay in scope. If you’re watching code write itself, you skipped the important part.

03 — Review

Your eyes first

Open it. Use it. Click things. Compare to your plan. Then ask the agent what it missed.

04 — Compound

Distill the session

Run /compound. Capture decisions, tradeoffs, dead ends. The next session starts smarter.

7 Transferable Principles

01

Context is everything

The agent only knows what you tell it. Quality output = quality context.

02

Planning > building

80% planning, 20% building. The plan is the real work.

03

Share your mental model

The agent starts from zero every time. Transfer your picture of the goal.

04

Review against the plan

Your judgment comes first. Then ask the agent for what you missed.

05

Recognise when to quit

Sunk cost is a trap. Starting fresh with better context is the skill.

06

It’s a conversation

Not a command line. Collaborate, ask questions, refine together.

07

Compound your sessions

Distill everything. Make the next session inherit what you figured out.
