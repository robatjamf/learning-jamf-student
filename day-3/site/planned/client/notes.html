Jamf & MDM

Jamf is a platform built specifically for managing Apple devices — Macs, iPhones, iPads, and Apple TVs — at scale. It sits in a category called Mobile Device Management (MDM), which lets IT teams remotely configure, secure, and manage devices without physically touching them.

Key Concepts

  • MDM protocol — An Apple-defined standard that lets management servers communicate with devices. Jamf Pro is built on top of this.
  • Jamf Pro — The enterprise product. Full device management, policy enforcement, software deployment, reporting.
  • Jamf School — Simplified version for K-12 education environments.
  • Jamf Protect — Endpoint security product layered on top of Jamf Pro.
  • Enrollment — The process of registering a device with Jamf Pro so it can be managed. Can be automated via ADE (Apple Device Enrollment) or done manually.
  • Policies — Actions applied to devices on a schedule or trigger (e.g. install software, run a script).
  • Configuration Profiles — XML documents that define device settings (Wi-Fi, VPN, restrictions). Deployed via MDM.
  • Smart Groups — Dynamic device groups built on criteria (OS version, department, model). Policies target groups, not individual devices.
  • Integration first — Jamf does not replace your existing IT stack. It integrates with Identity providers (Okta, Azure AD), SIEM, and ITSM tools like ServiceNow.
Deeper dive ›

The MDM protocol works by establishing a persistent check-in relationship between the device and the MDM server. Devices check in on a schedule (or are pushed to check in via APNs — Apple Push Notification Service). When they check in, the server can deliver configuration profiles, commands (lock, wipe, install app), or queries (get device inventory).

This means Jamf Pro never directly talks to a device in real time — it queues commands, and the device picks them up on next check-in. APNs is used to nudge the device to check in faster.

Supervision is an additional state that unlocks deeper management capabilities — things like preventing the removal of MDM, enforcing single-app mode, or silently installing apps. Devices become supervised during enrollment (ADE) or via Apple Configurator.

APIs & REST

An API (Application Programming Interface) is a defined way for two software systems to communicate. REST is the most common style for web APIs — it uses standard HTTP methods and URLs to create, read, update, and delete resources.

Key Concepts

  • Endpoint — A specific URL that represents a resource. Example: /api/v1/computers
  • HTTP Methods — GET (read), POST (create), PUT/PATCH (update), DELETE (remove).
  • Request — What you send: method + URL + headers + optional body.
  • Response — What you get back: status code + headers + body (usually JSON or XML).
  • Status Codes — 200 OK, 201 Created, 400 Bad Request, 401 Unauthorised, 403 Forbidden, 404 Not Found, 500 Server Error.
  • REST principles — Stateless (server doesn't remember previous requests), resource-based URLs, standard HTTP methods, consistent format.
  • API key / Bearer token — How you prove who you are when making requests. Sent in the Authorization header.
Deeper dive ›

REST (Representational State Transfer) is an architectural style, not a protocol. It defines constraints: statelessness, a uniform interface, client-server separation, and cacheability. An API that follows these constraints is called RESTful.

The "stateless" part is important: every request must contain all the information needed to understand it. The server does not store session state between requests. This is why Bearer tokens are sent with every request — the server cannot "remember" you authenticated 5 minutes ago.

Jamf Pro has two API generations: the Classic API (older, XML-based, uses /JSSResource/ paths) and the modern Jamf Pro API (JSON-based, uses /api/v1/ paths). Both coexist; new functionality is added to the modern API only.

Webhooks

A webhook is an automated HTTP POST request that a system sends to a URL you specify when a particular event happens. Instead of you asking "did anything change?" repeatedly (polling), the system tells you the moment it does (push).

Key Concepts

  • Event-driven — Webhooks only fire when something happens. No event = no request.
  • Payload — The data sent in the webhook's POST request body. Usually JSON or XML. Contains information about the event (what happened, to which resource, and when).
  • Endpoint (receiver) — A URL you expose that listens for incoming POST requests from the webhook sender.
  • Push vs Pull — Webhooks are push. Polling (repeated GET requests on a schedule) is pull. Push is more efficient for real-time events.
  • Reliability — Webhooks can fail if your endpoint is down. Good implementations include retry logic and signature verification.
  • Signature verification — The sender includes a hash of the payload using a shared secret. You verify this hash to confirm the request came from the expected source.
Deeper dive ›

Jamf Pro webhooks fire on device events: enrollment, check-in, policy completion, inventory update, and more. You configure the event type and destination URL in Jamf Pro settings. When the event fires, Jamf POSTs the payload immediately.

The payload in the workshop arrived as XML and contained the device ID, event type, and timestamp. This is typical of the Jamf Classic webhook format. The modern API supports JSON payloads for newer event types.

Testing webhooks during development: tools like webhook.site or ngrok let you receive webhooks on a public URL while developing locally. Once your handler is working, you deploy it to a real server.

Authentication & Authorisation

Authentication is proving who you are. Authorisation is determining what you are allowed to do. Both are required for secure API access — you must be identified before the system can decide what you can access.

Key Concepts

  • Authentication (AuthN) — Proving identity. "I am Ron." Methods: password, token, certificate, biometric.
  • Authorisation (AuthZ) — Determining permissions. "Ron is allowed to read devices but not delete them."
  • Bearer token — A string passed in the Authorization: Bearer <token> header. The server trusts whoever holds the token.
  • API key — A long random string tied to an account. Simpler than OAuth but less granular.
  • OAuth 2.0 — A delegation framework. Lets you grant a third-party app access to your account without giving it your password. Used by Jamf Pro for modern API access.
  • JWT (JSON Web Token) — A self-contained token that encodes claims (user ID, roles, expiry) and is cryptographically signed. Servers can verify JWTs without a database lookup.
  • Token expiry — Tokens have a TTL (time to live). After expiry, you must re-authenticate to get a new token.
Deeper dive ›

Jamf Pro's modern API uses OAuth 2.0 with the client credentials flow: you provide a client ID and client secret, the server returns a Bearer token with a defined expiry. Your code stores and reuses this token until it expires, then fetches a new one.

The classic API used Basic auth (base64-encoded username:password in the Authorization header). This is less secure because credentials travel with every request — a single intercepted request exposes your password. Bearer tokens are scoped and expire, limiting the blast radius if one is stolen.

The principle of least privilege applies here: grant API credentials only the permissions they actually need. Read-only credentials for a reporting tool; write permissions only for automation that creates resources.

JSON & XML

JSON and XML are two formats for structuring and transmitting data between systems. Both represent the same types of data — strings, numbers, lists, nested objects — but with very different syntax. JSON is lighter and more readable; XML is more verbose but supports richer metadata.

Key Concepts

  • JSON — JavaScript Object Notation. Key-value pairs in curly braces. Arrays in square brackets. Lightweight, widely supported.
  • XML — Extensible Markup Language. Tag-based like HTML. Every value is wrapped in opening and closing tags. More verbose.
  • When to use JSON — Modern REST APIs, configuration files, data exchange between web services.
  • When to use XML — Legacy systems, macOS configuration profiles, Jamf Classic API, SOAP web services.
  • Parsing — Converting the raw text format into objects your code can work with. Every language has built-in JSON/XML parsers.
Deeper dive ›

Same data, two formats:

// JSON
{
  "device": {
    "id": 42,
    "name": "Ron's MacBook Pro",
    "enrolled": true
  }
}

<!-- XML -->
<device>
  <id>42</id>
  <name>Ron's MacBook Pro</name>
  <enrolled>true</enrolled>
</device>

XML has advantages: it supports attributes, namespaces, schemas (XSD), and is the backbone of macOS configuration profiles (which are property list / plist files — a subset of XML). JSON has advantages: shorter, easier to read, native to JavaScript, faster to parse in most contexts.

HTTP Fundamentals

HTTP (HyperText Transfer Protocol) is the foundation of data communication on the web. Every time you call an API, load a webpage, or a webhook fires, it uses HTTP. HTTPS is the encrypted version — the same protocol over a TLS connection.

Key Concepts

  • Request / Response cycle — Client sends a request; server sends a response. Every HTTP interaction follows this pattern.
  • Methods — GET, POST, PUT, PATCH, DELETE. Each has a defined semantics.
  • Headers — Metadata about the request or response. Content-Type, Authorization, Accept, Cache-Control.
  • Status codes — 1xx informational, 2xx success, 3xx redirect, 4xx client error, 5xx server error.
  • Body — The payload. Requests with a body (POST, PUT) include data. Responses include the returned data.
  • HTTPS / TLS — Encrypts the connection so headers and body cannot be read in transit. Required for any production API.
Deeper dive ›

Common status codes to know: 200 OK (success), 201 Created (POST succeeded, resource created), 204 No Content (success, nothing to return — common on DELETE), 400 Bad Request (your request is malformed), 401 Unauthorised (no credentials or invalid token), 403 Forbidden (authenticated but not permitted), 404 Not Found (resource does not exist), 429 Too Many Requests (rate limited), 500 Internal Server Error (server-side bug).

HTTP/2 and HTTP/3 are newer versions that improve performance with multiplexing (multiple requests over one connection) and QUIC (faster connection setup). The API interaction pattern remains the same — the transport is just more efficient.

VMs & Infrastructure

A virtual machine (VM) is a software-based computer that runs inside a physical host machine. It has its own OS, CPU allocation, RAM, and disk — but shares the physical hardware of the host. VMs are used for isolation, testing, replication, and running multiple environments on one machine.

Key Concepts

  • Hypervisor — The software layer that creates and manages VMs. Abstracts hardware and divides it among guest OS instances. Types: Type 1 (bare-metal, e.g. ESXi) and Type 2 (hosted, e.g. Parallels, VirtualBox).
  • Host / Guest — Host is the physical machine; guests are the VMs running on it.
  • Snapshot — A saved state of a VM at a point in time. You can revert to a snapshot if something breaks.
  • Image — A packaged VM template you can clone. Tart uses OCI-compatible images.
  • Isolation — What happens inside a VM (file changes, installed software, network traffic) does not affect the host or other VMs (unless explicitly bridged).
  • Tart — A macOS CLI for Apple Silicon VMs using Apple's Virtualization framework. Fast, native, no licence fees.
Deeper dive ›

Apple's Virtualization framework (available since macOS 12) allows Apple Silicon Macs to run macOS and Linux VMs natively — with near-native performance and minimal overhead. This is what Tart uses under the hood. Prior to Apple Silicon, macOS VMs on Mac required emulation, which was significantly slower.

VMs are fundamental to IT testing: you can spin up a clean macOS VM, enroll it into Jamf Pro, test a policy, observe results, and delete it — without affecting any real hardware. This is how you safely test configurations before deploying them to production devices.

Linux & Shell Basics

Linux is an open-source operating system used widely for servers, VMs, and infrastructure. The shell (command line) is the primary interface for interacting with Linux systems. Most server infrastructure — including web servers, APIs, and databases — runs on Linux.

Key Concepts

  • Shell — A program that accepts text commands and executes them. Bash and Zsh are common shells.
  • File system — Everything in Linux is a file. The root is /. Common directories: /home (user files), /etc (config files), /var (logs, runtime data), /usr (installed software).
  • Permissions — Files have owner, group, and world permissions. rwx = read/write/execute. chmod changes permissions; chown changes ownership.
  • sudo — Run a command as superuser (root). Required for system-level changes.
  • Package manager — apt (Debian/Ubuntu) or yum/dnf (RHEL/Fedora) for installing software.
  • Process management — ps, top, kill, systemctl for managing running services.
Deeper dive › 
# Navigation
pwd             # current directory
ls -la          # list files with details + hidden
cd /etc         # change directory
cd ..           # go up one level

# Files
cat file.txt    # print file content
nano file.txt   # edit a file (simple editor)
cp a.txt b.txt  # copy a file
mv a.txt /tmp/  # move/rename a file
rm file.txt     # delete a file

# Permissions
chmod 755 script.sh   # rwxr-xr-x
chmod +x script.sh    # make executable
sudo chown ron:ron file.txt

# Packages (Ubuntu/Debian)
sudo apt update
sudo apt install nginx

# Services
sudo systemctl start nginx
sudo systemctl enable nginx   # start on boot
sudo systemctl status nginx

Networking Basics

Networking is how computers communicate — locally and over the internet. Understanding IP addresses, ports, and the difference between LAN and WAN is essential for hosting services, debugging connectivity issues, and understanding how Jamf Pro communicates with devices.

Key Concepts

  • IP Address — A unique numerical address for a device on a network. IPv4 (e.g. 192.168.1.10) or IPv6.
  • LAN — Local Area Network. Devices on the same local network (e.g. your home Wi-Fi). Private IP ranges: 192.168.x.x, 10.x.x.x.
  • WAN — Wide Area Network. The internet. Your router has a public IP; devices on your LAN share it via NAT.
  • Port — A numbered channel on a device. HTTP uses port 80; HTTPS uses 443; SSH uses 22. One IP can serve many services via different ports.
  • DNS — Domain Name System. Translates human-readable names (jamf.com) into IP addresses. Like a phone book for the internet.
  • Firewall — Controls which inbound/outbound connections are allowed by port and protocol.
  • NAT — Network Address Translation. Your router maps private IPs to one public IP for outbound traffic.
Deeper dive ›

To host a site on a VM that other LAN devices can access: find the VM's LAN IP with tart ip <name> or hostname -I inside the VM. Run a web server on port 80. Other devices on the same network can reach it at http://<vm-ip>.

To make a LAN service accessible from the internet, you need port forwarding on your router (map a public port to the VM's private IP) or a tunnel tool like ngrok, which creates a public HTTPS URL that proxies to your local server.

Jamf Pro communicates with managed devices over port 443 (HTTPS). APNs (Apple Push Notification Service) uses port 443 outbound and 2195/2196 for the legacy binary protocol. Firewalls must allow these for MDM to function.

macOS Management

Managing macOS at scale means deploying software, enforcing settings, running scripts, and maintaining compliance — all without touching each device individually. Jamf Pro orchestrates this through a combination of configuration profiles, policies, packages, and the MDM protocol.

Key Concepts

  • Configuration Profiles — XML files that define device settings (Wi-Fi, VPN, password policy, restrictions). Deployed via MDM and applied at the system level.
  • Policies — Jamf Pro-specific constructs that define actions: install a package, run a script, update inventory. Trigger: recurring check-in, login, startup, or manual.
  • Packages (.pkg) — The macOS format for installable software. Jamf Pro hosts and deploys packages to devices via policy.
  • Scripts — Shell scripts run on managed devices during policy execution. Used for tasks profiles cannot handle (modifying config files, custom setup logic).
  • ADE (Automated Device Enrollment) — Apple's zero-touch deployment program. Devices are pre-assigned to an MDM server — the moment they are powered on and connected to the internet, they enroll automatically.
  • Inventory — Jamf Pro collects hardware and software details from each device. Updated on check-in. Used for Smart Group membership criteria.
Deeper dive ›

The macOS management hierarchy: Device → MDM enrollment → Configuration Profiles (settings) + Policies (actions). Profiles are stateful — removing the profile reverses the setting. Policies are one-time actions or scheduled tasks.

User-Approved MDM vs. Supervised MDM: user-approved means the user manually approved MDM during setup (more limited control). Supervised (via ADE or Apple Configurator) gives IT deeper control — silent app installs, preventing MDM removal, enabling features unavailable otherwise.

Git & Version Control

Git is a distributed version control system. It tracks every change ever made to files in a repository, lets multiple people collaborate without overwriting each other's work, and makes it possible to go back to any previous state. It is the standard tool for managing code in almost every software project.

Key Concepts

  • Repository — A directory tracked by Git. Contains files and the full history of changes.
  • Commit — A saved snapshot of staged changes. Has a unique hash, message, author, and timestamp.
  • Branch — An independent line of development. The default is main. Create branches freely — they are cheap.
  • Merge — Combining one branch into another. Fast-forward (no divergence) or three-way merge (diverged histories).
  • Remote — A copy of the repo hosted elsewhere (GitHub, GitLab). origin is the conventional name for the primary remote.
  • Pull Request (PR) — A request to merge one branch into another, with code review. The standard collaboration pattern on GitHub.
  • Conflict — When two branches changed the same line differently. Git cannot auto-merge — you resolve it manually.
Deeper dive ›

Git's branching model enables the feature branch workflow: main is always stable and deployable. All work happens on feature branches. When a feature is complete and reviewed, it merges into main. This keeps production code clean.

Under the hood, a commit is a pointer to a tree (snapshot of file contents) plus metadata and a pointer to the parent commit. Branches are just lightweight pointers to a commit — that is why creating a branch is instantaneous regardless of repo size.

Automation & Scripting

Automation means replacing repetitive manual tasks with code that runs on its own. In an IT context, this means scripts that configure systems, APIs that trigger workflows, and scheduled jobs that keep environments consistent. If you do something more than twice, it should be automated.

Key Concepts

  • Bash script — A text file containing shell commands. Run it once, or schedule it. The lingua franca of system automation on macOS/Linux.
  • Idempotent — Running the same script multiple times produces the same result. Good automation is idempotent.
  • Cron — A Unix scheduler. Define jobs with a cron expression (minute, hour, day, month, weekday) to run commands on a schedule.
  • API automation — Using HTTP requests in scripts to interact with services programmatically. curl in bash; requests in Python; fetch in JavaScript.
  • Environment variables — Store secrets and config (API keys, URLs) outside your code. Never hardcode credentials in a script.
  • Exit codes — Scripts return 0 on success, non-zero on failure. Automation pipelines check exit codes to decide whether to continue.
Deeper dive › 
#!/bin/bash
# Simple Jamf token + API call in a script

JAMF_URL="https://your-instance.jamfcloud.com"
TOKEN=$(curl -s -X POST "$JAMF_URL/api/v1/auth/token" \
  -u "$JAMF_USER:$JAMF_PASS" \
  -H "Accept: application/json" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['token'])")

# Use the token
curl -s -X GET "$JAMF_URL/api/v1/computers-preview" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/json"

Credentials come from environment variables ($JAMF_USER, $JAMF_PASS) — never written in the script itself. The script gets the token first, then uses it for the real request. This is the standard pattern for scripted API access.

Identity & Access Management (IAM)

IAM is the set of processes and technologies that ensure the right people have access to the right resources — and nothing more. It is the layer that connects HR systems, authentication providers, and tools like Jamf Pro. Getting IAM right eliminates a massive category of manual IT work.

Key Concepts

  • Identity Provider (IdP) — The authoritative source of user identity. Examples: Okta, Azure Active Directory, Google Workspace.
  • SSO (Single Sign-On) — One login gives access to all connected apps. The IdP authenticates the user; apps trust the IdP.
  • SCIM — Protocol for automatically syncing user accounts between systems. When HR adds a new employee, SCIM provisions their accounts automatically.
  • LDAP — Older directory protocol. Still used by many enterprise systems. Azure AD and Okta can act as LDAP providers for legacy tools.
  • RBAC (Role-Based Access Control) — Permissions assigned to roles, not individuals. Users are assigned roles. Simpler to manage at scale.
  • Least privilege — Grant only the permissions a user or system actually needs. Nothing more.
  • Zero Trust — "Never trust, always verify." No implicit trust based on network location. Every access request is authenticated and authorised regardless of where it comes from.
Deeper dive ›

The Enterprise IT Admin persona from Day 1 illustrated the cost of missing IAM integration: she was manually creating accounts because HR, Identity, and Jamf Pro were not connected. The fix is a proper IAM flow: HR system → IdP (via SCIM) → all connected tools (Jamf Pro, Slack, Google Workspace, etc.) are provisioned automatically.

Jamf Pro integrates with LDAP and SAML-based SSO. User accounts and group memberships from the IdP can be used to drive Jamf Pro group membership and policy scoping — the IT admin never touches it after initial setup.

DevOps Fundamentals

DevOps is a set of practices that combines software development (Dev) and IT operations (Ops) to shorten development cycles and deliver changes reliably. The core idea: automate everything that can be automated, and make deployment a non-event rather than a high-risk ceremony.

Key Concepts

  • CI/CD — Continuous Integration / Continuous Deployment. Every code change is automatically tested (CI) and deployed to production (CD) with no manual steps.
  • Pipeline — The automated sequence of steps a code change goes through: build → test → lint → deploy.
  • Infrastructure as Code (IaC) — Defining server configuration and infrastructure in code (Terraform, Ansible) rather than clicking through UIs. Reproducible, version-controlled.
  • Container — A lightweight, isolated environment for running an application. Docker packages an app and its dependencies into a portable image.
  • Immutable infrastructure — Instead of updating a server, replace it with a new one built from a fresh image. Eliminates configuration drift.
  • Monitoring & observability — Logs, metrics, and traces that tell you what your system is doing in production.
Deeper dive ›

The connection to Jamf: Jamf Pro itself can be part of a DevOps-style workflow. Configuration profiles and policies can be version-controlled in Git. Changes go through a PR review process. A CI/CD pipeline can deploy updates to Jamf Pro via its API — the same pattern used for software deployments, applied to device management.

Tools in this space: GitHub Actions for CI/CD pipelines, Terraform for infrastructure, Ansible for configuration management, Docker for containers, and tools like jamf-upload or the Jamf Pro API for automating Jamf configuration deployment.

Claude Code

Claude Code is Anthropic's CLI for Claude — an AI assistant that operates directly in your terminal, reads your project files, and helps you build software through natural language conversation. It is not a chatbot that generates code for you to paste — it reads, writes, and edits files in your project directly.

Key Concepts

  • Terminal-first — Claude Code runs in your shell, not a browser. It has direct access to your filesystem and can run commands with your permission.
  • CLAUDE.md — Project context file. Claude reads this at the start of every session. Defines the project, conventions, and current state. Keep it lean.
  • COMPOUND.md — Session history file. Populated via /compound at the end of a session. Rich context: decisions, tradeoffs, dead ends.
  • Compound Engineering loop — Plan → Work → Review → Compound. A structured way to build iteratively with AI.
  • @ references — Type @filename in a prompt to reference a specific file. Claude reads it and uses it in context.
  • Plan mode — Enter with /plan. Claude describes what it will do before making any changes. Review and approve before it acts.
  • Memory — Persistent notes directory that survives between sessions. Global (~/.claude/MEMORY.md) and project-level.

Ron's take

The planning phase — the interview, the self-reflection, the iterative plan review — was the longest part of Day 3 by far. That time felt excessive in the moment but it directly caused everything to match the plan in the end. The one-shot page, built without any context, produced a basic 3-card summary. The planned site is a full multi-page reference tool. Same AI, completely different result. Context is the variable. Working this way also shifts where your effort goes: instead of worrying about individual lines of code, you're thinking about architecture — how pieces connect and what the system should actually do.

Deeper dive ›

Claude Code's power comes from context: the more relevant context you give it (via CLAUDE.md, @ references, and conversation history), the more accurate and useful its output. Vague prompts produce vague results. Specific prompts with file references and constraints produce precise results.

The Compound Engineering loop is designed to counteract the tendency to rush. Skipping planning leads to code that technically works but does not fit the real requirement. The review step forces you to evaluate what was built against what was intended — and compound captures the learning so future sessions do not repeat the same mistakes.

AI & LLMs

Large Language Models (LLMs) are AI systems trained on vast amounts of text to predict and generate human-like language. They power tools like Claude, ChatGPT, and Gemini. Understanding how they work helps you use them more effectively and understand their limitations.

Key Concepts

  • LLM — Large Language Model. A neural network with billions of parameters trained on text to predict the next token in a sequence.
  • Token — The unit of text an LLM processes. Roughly 3-4 characters or 0.75 words. "Hello world" = 2 tokens.
  • Context window — The maximum number of tokens the model can process at once (input + output). Exceeding it causes earlier content to be dropped.
  • Temperature — Controls randomness. 0 = deterministic (always picks the most likely token). 1+ = more creative and varied output.
  • Hallucination — When the model generates plausible-sounding but incorrect information. Happens because it generates tokens probabilistically, not by looking up facts.
  • System prompt — Instructions given to the model before the conversation starts. Defines its role, constraints, and context.
  • Fine-tuning — Additional training on a specific dataset to specialise the model's behaviour. Different from prompting — it changes the model weights.
  • RAG (Retrieval-Augmented Generation) — Augmenting an LLM with real-time document retrieval. The model gets relevant docs injected into context before generating — reduces hallucinations for factual queries.
Deeper dive ›

LLMs do not "know" things the way a database does. They learn statistical patterns from text. When you ask a question, the model generates a response that is statistically likely given the prompt and its training — not a lookup. This is both the source of their impressive generalisation and their tendency to hallucinate.

Practical implications: always verify factual claims, especially for niche topics, recent events (after the model's training cutoff), or specific version numbers. Use the model for reasoning, drafting, and transformation tasks — not as a source of truth for facts you can look up.

Claude's model family (as of 2026): Claude 4.x series. Haiku = fast and lightweight; Sonnet = balanced; Opus = most capable. Claude Code (the CLI) runs on Sonnet 4.6 by default.

Security

Security is the practice of protecting systems, data, and people from unauthorised access, damage, or disruption. In an Apple device management context, this spans endpoint security, identity security, network security, and the software supply chain.

Key Concepts

  • CIA Triad — Confidentiality (data is only seen by those authorised), Integrity (data is not altered without authorisation), Availability (systems are accessible when needed).
  • Endpoint security — Securing individual devices (the "endpoints"). Includes antivirus, EDR, configuration hardening, and patch management. Jamf Protect is Jamf's endpoint security layer.
  • Principle of least privilege — Grant only the access a user or process actually needs. Nothing more.
  • Zero Trust — Assume breach. Do not trust any user or device implicitly based on network location. Verify every access request.
  • Patch management — Keeping software and OS versions up to date to close known vulnerabilities. A core Jamf Pro use case.
  • Threat model — A structured analysis of what assets you are protecting, who might attack them, and how. Informs which security controls to prioritise.
  • OWASP Top 10 — The most critical web application security risks. Includes injection, broken authentication, XSS, and more. Relevant for anyone building APIs or web services.
Deeper dive ›

macOS has strong built-in security features: Gatekeeper (restricts app execution to signed/notarised software), SIP (System Integrity Protection, prevents modification of system files even by root), FileVault (full-disk encryption), and Secure Boot. Jamf Pro can enforce and report on these features via configuration profiles and compliance scripts.

For API security: never commit credentials to Git, always use HTTPS, rotate tokens regularly, implement rate limiting on your endpoints, and validate all input. The most common API vulnerabilities are poor authentication, excessive data exposure (returning more data than the client needs), and broken object-level authorisation (user A can access user B's data by changing an ID in the URL).

Prompt Engineering

Prompt engineering is the practice of designing inputs to an LLM to get better outputs. It is not magic — it is about giving the model the right context, constraints, and examples so it can generate what you actually need. Better prompts = better results, less back-and-forth.

Key Concepts

  • System prompt — Instructions given before the conversation. Defines the model's role, tone, and constraints. In Claude Code, CLAUDE.md serves this function.
  • Few-shot prompting — Providing examples of input/output pairs in the prompt. The model learns the pattern from examples and applies it to your request.
  • Chain of thought — Asking the model to "think step by step" before giving an answer. Improves accuracy on reasoning tasks.
  • Context — The more relevant context you give (files, constraints, examples, goals), the better the output. Vague prompts produce vague results.
  • Constraints — Tell the model what NOT to do, what format to use, what length to target. Constraints reduce unnecessary variation.
  • Iteration — Prompting is iterative. A first attempt rarely gets you exactly what you need. Refine based on output.
  • Hallucination mitigation — Ground the model with reference documents, use retrieval, and verify outputs. Ask the model to cite its sources or flag uncertainty.

Role: You are a senior macOS systems engineer.
Task: Review this shell script and identify any security issues.
Context: This script runs as root during Jamf Pro policy execution.
Constraints: Focus only on security issues, not style. Be specific.
Output format: Bulleted list, one issue per bullet.

[paste script here]

Role + Task + Context + Constraints + Output format = consistently better results than a plain question. The model has everything it needs to generate a focused, useful response rather than a generic one.

In Claude Code specifically: the more you invest in CLAUDE.md and COMPOUND.md, the better each session goes. Claude reads the project context before responding — a well-maintained context file is the most powerful "prompt" you have.
