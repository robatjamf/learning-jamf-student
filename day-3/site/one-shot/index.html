Day 1 — What Is Jamf? Overview

What Jamf Does

"Jamf is a security platform exclusively designed for Apple devices."

Jamf lets IT teams manage Apple devices (Mac, iPhone, iPad) at scale — pushing settings, installing apps, enforcing security policies, and supporting users remotely. The surprise: Zero Touch — you can go from unboxing a MacBook to a fully configured device without ever touching it directly.

MDM vs DDM (Blueprints)

MDM (Mobile Device Management)

The classic model. Jamf Pro sends a command → device checks in → executes → reports back. More back-and-forth between server and device.

DDM / Blueprints (Declarative)

The device and Jamf Pro communicate directly using declarations. Less back-and-forth, faster, and the device manages its own state. The biggest Day 1 takeaway.

The Four Personas

Persona Scale Biggest Pain Point
Enterprise IT Admin 10,000+ devices Consistency and compliance at massive scale
K-12 IT Coordinator Multiple schools One person managing 3 campuses — can't be everywhere
Security Analyst 1,000+ alerts/day Alert fatigue, identifying real threats in the noise
Help Desk Technician Org-wide Remote troubleshooting without physical access
My group mapped the K-12 IT Coordinator — one person managing three campuses alone. Jamf lets them see which device has an issue and act on it remotely, without driving to the site.

Day 2 — VMs, APIs & Webhooks Technical

Virtual Machines

A computer running inside another computer. Its own OS, behaves like a real machine. On Day 2 I enrolled a Tart VM into Jamf Pro.

Think of it like a snow globe — a little world inside your world. You can reset it or throw it away without affecting anything outside.

tart clone <image>   # copy a base image
tart run <name>      # start the VM
tart ip <name>       # get its IP address
tart stop <name>     # shut it down

HTTP Methods — REST API

Think of it like a restaurant: you (client) send an order through the waiter (API) to the kitchen (server) and get food (data) back. On Day 2, I made a POST request in Postman and got back a created category in Jamf Pro.

GET

Read data. Fetch a list of computers or a policy. No changes made.

POST

Create something new. I created a category in Jamf Pro using POST.

PUT

Update an existing record. Replace or edit something already there.

DELETE

Remove a record permanently. Use with care.

JSON — The Data Format

Structured data that both humans and computers can read. Curly braces, colons, quotes. The webhook payload that arrived on Day 2 was in JSON format.

{
  "event": "ComputerEnrolled",
  "deviceName": "Sean-MacBook",
  "serialNumber": "C02XK1234567",
  "enrolled": true
}

Push vs Pull (Webhooks)

Push (Webhooks)

The server tells you when something happens — immediately. You don't have to ask. Like a doorbell: you don't check the door every 5 minutes, it rings when someone arrives.

Pull (Polling)

You keep asking "anything new?" over and over. Less efficient. Like a kid in the back seat: "Are we there yet? Are we there yet?"

Key Terms Expandable

Click any term to see the definition and analogy.

MDM — Mobile Device Management

A system for managing many devices from one place — pushing settings, installing apps, enforcing security rules.

Analogy: Like a school principal who can set rules for every classroom at once, instead of walking to each room individually.
DDM / Blueprints — Declarative Device Management

A newer, faster way for devices to manage themselves based on declarations. Less back-and-forth with the server. The device checks its own state and applies what's needed.

Key difference: MDM = Jamf tells the device what to do. DDM = the device knows what it should look like and gets there itself.
API — Application Programming Interface

A way for software to talk to other software. You send a request and get data back. Jamf Pro has a REST API you can call with tools like Postman.

Analogy: A restaurant — you tell the waiter (API) what you want, the waiter tells the kitchen (server), and you get your food (data) back.
Bearer Token — Authentication

A code that proves you've already logged in. You authenticate once, receive a token, and use it for all subsequent API requests.

Analogy: A wristband at an event. Show your ID at the door once, get the band, and flash it everywhere else without showing ID again.
Webhook

A URL that receives data when something happens. Instead of polling ("anything new?"), the server pushes data to you the moment an event fires.

Analogy: A doorbell. You don't check the door every five minutes — it rings when someone arrives.
Virtual Machine (VM)

A computer running inside another computer. It has its own OS and behaves like a separate machine. On Day 2, I used Tart to run a macOS VM and enrolled it in Jamf Pro.

Analogy: A snow globe — a little world inside your world. You can shake it, reset it, or throw it away without affecting the room you're in.
JSON — JavaScript Object Notation

A structured way to format data so both humans and computers can read it. Uses curly braces, colons, and quotes. This is what API responses and webhook payloads look like.

Analogy: Filling out a form — each field has a label and a value. {"name": "Sean", "role": "student"}

Day 3 — Building with Claude Code Process

The Compound Engineering Loop

Day 3 introduced a structured way to work with AI agents. The core idea: planning is the hard part. Execution is just confirmation.

Step 1

Plan

Define the goal clearly. Gather context. Answer the agent's questions before it starts building.

Step 2

Work

Execute with AI assistance. Stay within the plan. Don't let scope creep in.

Step 3

Review

Evaluate the output yourself first. Compare to what you planned. Then ask the agent what it missed.

Step 4

Compound

Distill decisions, tradeoffs, and discoveries into a reference. The next session inherits everything.

One-Shot vs Planned Build

One-Shot

Dump everything into one prompt and hope for the best. Fast to start, messy to finish. Good for comparison — kept in site/one-shot/.

Planned Build

Read the project first. Plan before building. Ask questions. This page is the result of the planned build. Lives in site/planned/.

Key Principles from Day 3

  • Context is everything — the agent only knows what you tell it
  • Planning > building — think before you build
  • Share your mental model — the agent doesn't have it automatically
  • Review against your plan — your eyes and judgment come first
  • Know when to quit — starting fresh with better context beats pushing through a bad path
  • Compound your sessions — distill everything so the next session inherits it
