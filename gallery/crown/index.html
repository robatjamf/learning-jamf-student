Section 01 — APIs in Jamf Pro

How software talks to Jamf Pro.

An API (Application Programming Interface) is a middleman between your tool and Jamf Pro's data. Think of it like a restaurant waiter — you tell the waiter what you want, the waiter goes to the kitchen, and brings the food back. You never touch the kitchen.

In Jamf Pro, APIs let you read device data, create policies, and automate actions without clicking through the UI.

The two requests you need to know

GET — Ask for information. "Give me the list of all enrolled Macs."

POST — Send something new. "Create this new user account."

PUT / PATCH — Update something that already exists.

DELETE — Remove a resource. Use carefully.

What a real Jamf API response looks like (JSON)

GET /api/v1/computers-preview — Example Response
{
  "totalCount": 42                  ← total devices
  "results": [
    {
      "id":         "1"             ← device ID
      "name":       "Crown's MacBook Pro"
      "managed":    true           ← enrolled in Jamf
      "username":   "crown"
    }
  ]
}

A Bearer Token goes in your request header to prove you are allowed to access the data. No token, no data — Jamf's security gate.

Section 02 — Personas in Jamf Pro

Who actually uses Jamf — and why it matters.

A persona is a fictional but realistic profile of a type of person who interacts with your system. It keeps you focused on real human needs instead of abstract features.

In Jamf Pro, different people have very different needs from the same platform. Understanding those personas shapes what you automate, what you restrict, and what you surface in the UI.

💻

IT Admin

Manages all devices, runs policies, deploys software. Needs power and automation.

👨‍💼

End User

Just wants their Mac to work. Needs a smooth, low-friction experience.

🔒

Security Officer

Needs compliance reports and device posture data. Cares about risk.

🏫

School Admin

Manages student iPads at scale. Needs simple controls and class-level management.

Why personas change your decisions

The same Jamf policy can feel like a helpful tool to an IT Admin and an annoying restriction to an End User. Building a persona forces you to consider both sides before you deploy.

Section 03 — How Claude Works

AI is not magic. Here is the actual model.

Claude is a Large Language Model (LLM) — trained on an enormous amount of text. It does not "think" the way humans do. It predicts the most likely next word (token) based on everything it has been trained on and everything you have told it in the current conversation.

The context window

Claude can only "see" a limited amount of text at once — this is called the context window. Think of it as short-term memory. The more context you give it (your project structure, requirements, past decisions), the better the output.

The Compound Engineering Loop

This is the workflow taught in Day 3. It turns AI from a guessing tool into a reliable collaborator.

One thing to watch out for

Hallucination — Claude can confidently produce wrong answers. This is why the Review step is non-negotiable. Your eyes are the final quality check, not Claude's.

Two files keep Claude on track across sessions: CLAUDE.md for project setup, and COMPOUND.md for decisions, tradeoffs, and history that carry forward.

Section 04 — Terminal Cheat Sheet

Commands you will actually use.

The terminal is how you talk to your computer directly. These are the commands that came up most during the training.

Claude Code
